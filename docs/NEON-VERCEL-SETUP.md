# Connecting a Neon database to your Vercel website

This is the database and hosting setup, in the order that works. It is written for a shop
owner, not a developer. You never need to read or edit a configuration file for this part:
the integration fills in the values, and this document tells you what to check.

Nothing here changes how the website works. It is the wiring that lets the website talk to
its own database.

## Before you start

- You have a Neon account, and it is yours. You keep ownership of it.
- You have a Vercel account with the barber website project in it.
- You have your copy of the template as your own GitHub repository.

## Step 1: Create the database in Neon

1. Sign in at neon.tech.
2. Create a project for this shop.
3. Keep the default branch, or name it `main`.
4. Leave the database name and role as Neon suggests unless you have a reason to change them.

You now own a PostgreSQL database that nobody else can see.

## Step 2: Turn on the Vercel integration inside Neon

1. In Neon, open **Integrations**.
2. Choose the **Vercel** integration.
3. Turn on a database branch for each preview deployment. This gives previews their own
   copy, so testing never writes into the shop's real data.
4. Choose **Install from Vercel Marketplace**.

## Step 3: Install it from Vercel

1. Open https://vercel.com/marketplace/neon
2. Choose **Link Existing Neon Account**, so it uses the account you already have rather
   than creating a second one.
3. Choose your Vercel team.
4. Choose **Specific Projects**, then select the barber website project. Do not grant access
   to every project if you only need this one.
5. Approve the permissions the integration asks for. In plain terms, it needs to read and
   write environment variables in the project you selected, and to create a database branch
   for each preview. It does not need to see your other projects.

## Step 4: Link the project

1. Select the barber website project when the integration asks which project to connect.
2. Confirm it is pointing at the database you created in Step 1.
3. Keep production connected to your production database branch. Preview deployments should
   follow their own branches, which the integration sets up for you.

## Step 5: Check it worked

Run these from the project folder. They read only; none of them changes anything.

```
npm run env:check       # is anything missing or malformed?
npm run env:doctor      # plain-language explanation of what each value is for
npm run client:preflight
```

Then confirm three things:

1. The database value exists and starts with `postgresql://`.
2. The website loads and can show a service.
3. A test booking completes.

If any of those fail, the next section says which value is missing.

## What the integration does not give you

Neon supplies the database connection. It does not supply the rest, and the website will
not run without them:

| Value | What it is | Where it comes from |
| --- | --- | --- |
| `NEXTAUTH_SECRET` | The key that keeps sign-in sessions private | Generated by you, or by the setup wizard |
| `NEXTAUTH_URL` | The address the site uses for sign-in | Your own domain, e.g. `https://yourshop.com` |
| `NEXT_PUBLIC_APP_URL` | The address used in links and emails | The same address |
| `UPSTASH_REDIS_REST_URL` | Shared rate limiting, so one visitor cannot overwhelm the shop | Your Upstash account |
| `UPSTASH_REDIS_REST_TOKEN` | The key for that rate limiting | Your Upstash account |

`npm run client:setup` walks these in order, generates a random `NEXTAUTH_SECRET` for you,
masks secret entry, keeps values that already work, and shows what it would do before it
does it. It does not rotate a working credential on its own.

Shared rate limiting is deliberately not optional in production. If it is missing the site
refuses to fall back to per-instance counting, because that would silently let a flood
through. That is a protection, not a bug.

## Which values are secret

| Value | Secret? | Notes |
| --- | --- | --- |
| `DATABASE_URL` | Yes | Contains the database password |
| `NEON_POSTGRES_PRISMA_URL` | Yes | Same, as an alternate name |
| `NEXTAUTH_SECRET` | Yes | Anyone with it can forge a session |
| `UPSTASH_REDIS_REST_TOKEN` | Yes | Grants access to your rate limiter |
| `NEXTAUTH_URL` | No | A plain address, but not something to publish either |
| `UPSTASH_REDIS_REST_URL` | No | A plain address, server side only |
| `NEXT_PUBLIC_APP_URL` | No | Public by design; never put a credential in a `NEXT_PUBLIC_` value |
| `NEXT_PUBLIC_APP_NAME` | No | Public by design |

`tests/env-classification.test.ts` enforces this table, so a future change cannot quietly
mark a credential public.

## The honest 30-minute claim

The clock starts when you already have both accounts and are willing to approve the
integration. From there, the five steps above are realistically 10 to 15 minutes.

The clock does not include: waiting for your domain's DNS to propagate, waiting for Vercel to
build, provider authorisation emails, or adding the four values the integration does not
provide. We will not claim a 30-minute setup for a shop that is still waiting on DNS, and this
document will not pretend otherwise.

## If something looks wrong

- **Every page returns an error after deploy:** the database value is missing or wrong. Run
  `npm run env:check`.
- **Sign-in loops back to the login page:** `NEXTAUTH_URL` does not match the address in the
  browser, or `NEXTAUTH_SECRET` changed after a session was created.
- **Booking fails only under load:** shared rate limiting is not configured, and the site is
  refusing to fall back. Add the two Upstash values.
- **Previews show the shop's real customers:** preview deployments are not using their own
  Neon branch. Re-check Step 2 item 3.
